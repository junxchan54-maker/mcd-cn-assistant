# 多人群点聚合：数据结构与分摊算法（能力四参考）

本文档定义能力四（多人群点聚合）的订单会话数据结构、分摊算法与账单模板。Agent 在实现能力四时按此执行。

---

## 一、设计定位（先读）

| 事项 | 结论 |
|---|---|
| 账户模型 | MCP 为**单账户鉴权**。本能力是**组织者模式**：全体成员餐品由下单人在会话内代录，最后用**下单人自己的账户**统一结算，其他人按账单向下单人支付 |
| 禁止事项 | **严禁模拟登录、代理登录或索取任何成员的账号 / 密码 / 验证码**；MCP 未开放多人购物车 API |
| 群聊形态 | 当前形态为"组织者在会话内代办"，**不是**群机器人，也**不是**实时多人并发的 H5；账单 HTML 仅作分享展示 |
| 收款 | Skill **不代收款项、不生成官方收款码**。账单给出每人应付金额，组织者用微信「群收款」或自己的收款码收款；HTML 账单可嵌入**组织者本人的**收款码图片 |

## 二、订单会话文件

路径：`<workspace>/.workbuddy/group-orders/yyyymmdd-hhmm-<N>人.json`
（首次开单时创建；每次增删改后回写；文件内不含任何账户凭证。）

```json
{
  "session_id": "20261012-1430-8人",
  "created_at": "2026-10-12 14:30",
  "status": "collecting",            // collecting | pricing | settled | ordered | closed
  "dining": {
    "mode": "delivery",              // delivery | pickup
    "store": null,                   // 确认后的门店信息（query-nearby-stores / delivery-query-stores 返回）
    "address": null                  // 外送地址（delivery-query-addresses 返回）
  },
  "organizer": "张三",               // 下单人（用其账户结算）
  "participants": ["张三", "李四", "王五"],
  "split_rules": {
    "delivery_fee": "even",          // even=均摊 | ratio=按消费比例 | person:张三=指定人承担
    "coupon_saving": "even",         // even=平摊 | organizer=归下单人
    "suggest_upsell": true           // 是否接受凑单建议
  },
  "items": [
    { "person": "张三", "meal_code": "MCP-xxxx", "name": "麦辣鸡腿堡", "qty": 1, "unit_price": 25.5, "added_at": "14:31" },
    { "person": "李四", "meal_code": "MCP-xxxx", "name": "麦辣鸡腿堡", "qty": 1, "unit_price": 25.5, "added_at": "14:33", "note": "不要辣" }
  ],
  "upsell": [],                      // 凑单建议被采纳后追加的条目，person 记为 "拼单凑单"
  "pricing": null                    // 算账阶段回填：calculate-price 结果 + 分摊明细
}
```

规则：

- `unit_price` 一律来自 `query-meals` / `query-meal-detail` 的返回，**不得由模型填写记忆价**；
- 同一人同餐品多条记录可直接合并 `qty`；
- "跟 XX 一样" → 复制该成员全部条目后回显确认；
- 会话跨轮次恢复时以文件为准，不依赖模型记忆。

## 三、智能算账引擎

### 3.1 满减凑单判定

输入：全员商品小计 `T`，满减档位列表 `[(t1, d1), (t2, d2), ...]`（来自 `query-promotions` / `query-store-coupons` / `available-coupons`）。

```
net(T) = T - max{ d_i : T >= t_i }        # 当前净支付
对每个候选小额单品（价格 p，如派 / 圆筒）：
  benefit = net(T) - (net(T + p) + p)     # 加购后总支出变化
  若 benefit > 0：建议加购，文案注明「多花 ¥p，多省 ¥benefit」
```

约束：

- 建议必须先用 `calculate-price` 实算验证（把候选组合整体送算），**不得用档位文字推断**；
- 采纳与否由成员确认，**绝不自动加购**；
- 一次最多给 1~2 个凑单建议（限流友好）。

### 3.2 券归属

- 结算账户固定为**下单人**：`query-my-coupons` / `query-store-coupons` 查下单人账户券，带入 `calculate-price`；
- 账单必须标注优惠归属：
  - `coupon_saving: organizer` → 「券省 ¥X 归下单人」
  - `coupon_saving: even` → 「券省 ¥X 平摊，每人减 ¥X/N」
- **下单前最后一次重算**：若 `create-order` 因券失效报错，**立即停止并回滚提示**，不自动重试扣款。

### 3.3 配送费分摊

配送费 `F` 以 `calculate-price` 返回为准（不同门店/时段可能免配或浮动）：

| 规则 | 算法 |
|---|---|
| `even` | `F/N` 逐项到分（银行家舍入），**最后一人的配送费 = F − 其他人之和**（尾差兜底） |
| `ratio` | 每人 `F × (个人小计 / T)` 逐项到分，尾差并入消费额最高的一人 |
| `person:X` | 全额记入 X 的应付 |

### 3.4 分摊总算法（尾差兜底原则）

优惠总额 `D`（满减 + 券，按 split_rules.coupon_saving 决定是否分摊）与配送费 `F` 分摊后：

```
每人应付_i = 个人小计_i − 分摊优惠_i + 分摊配送费_i
约束：Σ每人应付 == 实付总额（calculate-price 返回的应付）
实现：前 N−1 人逐项四舍五入到分，第 N 人 = 实付总额 − 其余人之和
     （保证账单合计与实付严格相等，尾差不超过 ±0.01 元 × (N−1)，落在最后一人）
```

若采用 `coupon_saving: organizer`，则优惠不分摊：`每人应付_i = 个人小计_i + 分摊配送费_i`，总优惠直接体现在下单人实付中。

## 四、账单模板

### 4.1 对话内 Markdown 账单

```markdown
🧾 麦当劳群点账单 | 2026-10-12 14:30 | 麦当劳（XX店）· 外送

| 成员 | 餐品 | 小计 | 分摊优惠 | 分摊配送费 | 应付 |
|---|---|---|---|---|---|
| 张三 | 麦辣鸡腿堡×1 | ¥25.50 | -¥3.00 | ¥2.25 | **¥24.75** |
| 李四 | 麦辣鸡腿堡×1（不要辣） | ¥25.50 | -¥3.00 | ¥2.25 | **¥24.75** |
| 王五 | 麦麦鸡×2, 可乐×1 | ¥36.00 | -¥4.00 | ¥3.00 | **¥35.00** |
| 拼单凑单 | 香芋派×1（跨满减档） | ¥9.00 | -¥1.00 | ¥0.75 | **¥8.75** |
| **合计** |  | **¥96.00** | **-¥11.00** | **¥8.25** | **¥93.25** |

💳 券「满 90 减 8」省 ¥8 + 门店满减省 ¥3：按平摊规则已计入每人「分摊优惠」。
🛵 配送费 ¥8.25：按人数均摊。
💰 收款：请向下单人 @张三 支付「应付」列金额（建议微信群收款，逐个按金额）。
```

### 4.2 HTML 账单（可选分享页）

- 由 Agent 按上表渲染为单文件 HTML（内联样式，无外部依赖），保存到会话文件同目录；
- 若组织者提供了自己的收款码图片路径，`<img>` 嵌入页首；未提供则留「请向下单人支付 X 元」占位说明；
- 不引入任何支付 SDK、不发起任何网络收款请求。

## 五、成员话术约定（会话内）

| 成员说 | Agent 行为 |
|---|---|
| 「张三 麦辣鸡腿堡×1 可乐×1」 | 追加条目，回显增量列表 |
| 「李四跟张三一样」 | 复制张三全部条目给李四，回显确认 |
| 「王五撤销」 | 删除王五全部条目（或指定条目），回显 |
| 「收完了 / 就这些人」 | 进入算账阶段（阶段三） |
| 「再看看能不能更省」 | 重跑凑单判定与券比较 |
| 「成单 / 下单吧」 | 生成账单 → 组织者确认 → 单账户 create-order |
