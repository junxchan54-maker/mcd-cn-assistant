# 多人群点聚合：数据结构与分摊算法（能力四参考）

本文档定义能力四（多人群点聚合）的订单会话数据结构、分摊算法与账单模板。Agent 在实现能力四时按此执行。

---

## 一、设计定位（先读）

| 事项 | 结论 |
|---|---|
| 账户模型 | MCP 为**单账户鉴权**。本能力是**组织者模式**：全体成员餐品由下单人在会话内代录，最后用**下单人自己的账户**统一结算，其他人按账单向下单人支付 |
| 禁止事项 | **严禁模拟登录、代理登录或索取任何成员的账号 / 密码 / 验证码**；MCP 未开放多人购物车 API |
| 群聊形态 | 当前形态为"组织者在会话内代办"，**不是**群机器人，也**不是**实时多人并发的 H5；账单 HTML 仅作分享展示 |
| 收款 | Skill **不代收款项、不生成官方收款码**。账单给出每人应付金额，组织者用微信「群收款」或自己的收款码收款；HTML 账单可嵌入**组织者本人的**收款码图片 |

## 二、订单会话文件

路径：`<workspace>/.workbuddy/group-orders/yyyymmdd-hhmm-<N>人.json`
（首次开单时创建；每次增删改后回写；文件内不含任何账户凭证。）

```json
{
  "session_id": "20261012-1430-8人",
  "created_at": "2026-10-12 14:30",
  "status": "collecting",            // collecting | pricing | settled | ordered | closed
  "dining": {
    "mode": "delivery",              // delivery | pickup
    "store": null,                   // 确认后的门店信息（query-nearby-stores / delivery-query-stores 返回）
    "address": null                  // 外送地址（delivery-query-addresses 返回）
  },
  "organizer": "张三",               // 下单人（用其账户结算）
  "participants": ["张三", "李四", "王五"],
  "split_rules": {
    "public_fee": "even",            // 公共费用（配送费 + 打包费）分摊：even=均摊 | ratio=按消费比例 | person:张三=指定人承担
    "coupon_saving": "even",         // even=平摊 | organizer=归下单人
    "suggest_upsell": true           // 是否接受凑单建议
  },
  "items": [
    { "person": "张三", "meal_code": "MCP-xxxx", "name": "麦辣鸡腿堡", "qty": 1, "unit_price": 25.5, "added_at": "14:31" },
    { "person": "李四", "meal_code": "MCP-xxxx", "name": "麦辣鸡腿堡", "qty": 1, "unit_price": 25.5, "added_at": "14:33", "note": "不要辣" }
  ],
  "upsell": [],                      // 凑单建议被采纳后追加的条目，person 记为 "拼单凑单"
  "pricing": null                    // 算账阶段回填：calculate-price 结果 + 分摊明细
}
```

规则：

- `unit_price` 一律来自**当前渠道**的 `query-meals` / `query-meal-detail` 的返回，**不得由模型填写记忆价**；注意**外送（orderType=2）与到店（orderType=1）是两套菜单价**（实测：脆薯饼 到店 ¥8.5 / 外送 ¥9.5；猪柳蛋麦满分 到店 ¥18 / 外送 ¥18.5），不可跨渠道复用；
- 同一人同餐品多条记录可直接合并 `qty`；
- "跟 XX 一样" → 复制该成员全部条目后回显确认；
- 会话跨轮次恢复时以文件为准，不依赖模型记忆。

## 三、智能算账引擎

### 3.1 满减凑单判定

输入：全员商品小计 `T`，满减档位列表 `[(t1, d1), (t2, d2), ...]`（来自 `query-promotions` / `query-store-coupons` / `available-coupons`）。

```
net(T) = T - max{ d_i : T >= t_i }        # 当前净支付
对每个候选小额单品（价格 p，如派 / 圆筒）：
  benefit = net(T) - (net(T + p) + p)     # 加购后总支出变化
  若 benefit > 0：建议加购，文案注明「多花 ¥p，多省 ¥benefit」
```

约束：

- 建议必须先用 `calculate-price` 实算验证（把候选组合整体送算），**不得用档位文字推断**；
- 采纳与否由成员确认，**绝不自动加购**；
- 一次最多给 1~2 个凑单建议（限流友好）；
- **无档位时不要臆造**：若 `calculate-price` 返回中**没有** `enjoyable` / `enjoyable.balance`（当前订单无可享受/可跨越的满减档位），直接说明"本单无凑单空间"，**不要凭想象编出满减门槛**。✅ 实测样例：某 5 人外送单返回无 `enjoyable` 字段 → 正确结论是"无可跨档位，不给加购建议"。

### 3.2 券归属

- 结算账户固定为**下单人**：`query-my-coupons` / `query-store-coupons` 查下单人账户券，带入 `calculate-price`；
- 账单必须标注优惠归属：
  - `coupon_saving: organizer` → 「券省 ¥X 归下单人」
  - `coupon_saving: even` → 「券省 ¥X 平摊，每人减 ¥X/N」
- **下单前最后一次重算**：若 `create-order` 因券失效报错，**立即停止并回滚提示**，不自动重试扣款。

### 3.3 公共费用分摊（配送费 + 打包费）

> **公共费用 = 配送费 `deliveryPrice` + 打包费 `packingPrice`**，两者都以 `calculate-price` 返回为准。
> ⚠️ 外送单（`orderType=2`）除配送费外**一定会有打包服务费**，且打包费本身可能自带优惠（原始 `packingOriginalPrice` → `packingPrice`）。**只分摊配送费会导致账单合计小于实付**，务必把打包费一并计入。到店单（`orderType=1`）通常无这两项。

记公共费用合计为 `F = deliveryPrice + packingPrice`（单位：分），按规则分摊：

| 规则 | 算法 |
|---|---|
| `even` | `F/N` 逐项到分（银行家舍入），**最后一人的公共费用 = F − 其他人之和**（尾差兜底） |
| `ratio` | 每人 `F × (个人小计 / T)` 逐项到分，尾差并入消费额最高的一人 |
| `person:X` | 全额记入 X 的应付 |

### 3.4 小计口径与分摊总算法

**小计口径（必须先定，否则账单对不上）**

- **用了券的成员，其"小计"取「券前基准价」**：`小计_i = 券后现价_i + 该成员所用券的省额_i`；
- 未用券的成员：`小计_i` 直接取 `calculate-price` 的 `productList.subtotal`（已含门店自动促销优惠）；
- **反例（实测踩坑）**：若对用券成员也直接用券后现价（如 ¥9.90，已含券省 ¥9.10）再做"券省平摊"，券省会被**重复扣减**，Σ每人应付与实付的差额**恰好等于券省额**（实测差 ¥9.10）。用券前基准价（¥19.00）即可对齐。

**总算法**

优惠总额 `D`（券省，按 `split_rules.coupon_saving` 决定是否分摊）与公共费用 `F` 分摊后：

```
每人应付_i = 小计_i − 分摊券省_i + 分摊公共费用_i
约束：Σ每人应付 == 实付总额（calculate-price 返回的 price）
实现：前 N−1 人逐项四舍五入到分，第 N 人 = 实付总额 − 其余人之和
     （保证账单合计与实付严格相等，尾差落在最后一人）
自检：脚本/流程中必须断言 Σ每人应付 == 实付，不等则说明口径错了（先查 3.4 第 1 条）
```

若采用 `coupon_saving: organizer`，则优惠不分摊：`每人应付_i = 小计_i + 分摊公共费用_i`，总优惠直接体现在下单人实付中。

> ✅ 实测样例（5 人外送，门店 storeCode 1421053）：券前小计合计 ¥111.70 − 分摊券省 ¥9.10 + 公共费用 ¥9.00（配送费 ¥6.00 + 打包费 ¥3.00）= **应付 ¥111.60 = 实付 ¥111.60**。其中按 `ratio` 分摊公共费用若用券后现价口径会出现 −1 分尾差，兜底逻辑正确将其并入消费额最高者。

## 四、账单模板

### 4.1 对话内 Markdown 账单

```markdown
🧾 麦当劳群点账单 | 2026-10-12 14:30 | 麦当劳（XX店）· 外送 | 共 5 人

| 成员 | 餐品 | 券前小计 | 分摊券省 | 分摊公共费 | 应付 |
|---|---|---|---|---|---|
| 张三 👑 | 麦辣鸡腿堡×1 | ¥25.50 | -¥1.82 | ¥1.76 | **¥25.44** |
| 李四 | 麦辣鸡腿堡×1（不要辣） | ¥25.50 | -¥1.82 | ¥1.76 | **¥25.44** |
| 王五 | 麦麦鸡×2，可乐×1 | ¥36.00 | -¥1.82 | ¥2.48 | **¥36.66** |
| 赵六 | 麦麦鸡×1，香芋派×1 | ¥25.00 | -¥1.82 | ¥1.72 | **¥24.90** |
| 钱七 | 中杯冰美式×1 | ¥19.00 | -¥1.82 | ¥1.28 | **¥18.46** |
| **合计** |  | **¥131.00** | **-¥9.10** | **¥9.00** | **¥130.90** |

💳 券「9.9元中杯冰美式」省 ¥9.10（原价 ¥19.00 → 券后 ¥9.90）：按平摊规则每人减 ¥1.82。
🛵 公共费用 ¥9.00（配送费 ¥6.00 + 打包费 ¥3.00）：按消费比例分摊。
🛒 凑单判定：算价未返回可享受优惠（enjoyable）→ 本单无可跨满减档位，未加购。
💰 收款：请向下单人 @张三 支付「应付」列金额（建议微信群收款，逐个按金额）。
✅ 校验：Σ每人应付 = 实付总额。
```

字段含义（**列名不可随意改**，否则口径容易串）：
- **券前小计**：用券成员 = 券后现价 + 券省额；未用券成员 = `productList.subtotal`；
- **分摊券省**：券省额按 `coupon_saving` 规则分摊后的每人份额（负数表示减钱）；
- **分摊公共费**：配送费 + 打包费按 `public_fee` 规则分摊后的每人份额；
- **应付**：`券前小计 − 分摊券省 + 分摊公共费`，Σ 必须等于实付总额。

### 4.2 HTML 账单（可选分享页）

- 由 Agent 按上表渲染为单文件 HTML（内联样式，无外部依赖），保存到会话文件同目录；
- 若组织者提供了自己的收款码图片路径，`<img>` 嵌入页首；未提供则留「请向下单人支付 X 元」占位说明；
- 不引入任何支付 SDK、不发起任何网络收款请求。

## 五、成员话术约定（会话内）

| 成员说 | Agent 行为 |
|---|---|
| 「张三 麦辣鸡腿堡×1 可乐×1」 | 追加条目，回显增量列表 |
| 「李四跟张三一样」 | 复制张三全部条目给李四，回显确认 |
| 「王五撤销」 | 删除王五全部条目（或指定条目），回显 |
| 「收完了 / 就这些人」 | 进入算账阶段（阶段三） |
| 「再看看能不能更省」 | 重跑凑单判定与券比较 |
| 「成单 / 下单吧」 | 生成账单 → 组织者确认 → 单账户 create-order |
